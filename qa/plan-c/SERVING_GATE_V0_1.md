## Billing mechanics and conditional arithmetic

The [Dedicated overview](https://docs.tokenfactory.nebius.com/ai-models-inference/dedicated-endpoints/overview) says per-GPU-hour billing with **per-minute granularity**. The [billing policy](https://docs.tokenfactory.nebius.com/ai-models-inference/dedicated-endpoints/billing-policy) says provisioning/not-ready is not billed, ready with running replicas is billed, and stopping with zero replicas is not billed. The [operations guide](https://docs.tokenfactory.nebius.com/ai-models-inference/dedicated-endpoints/operating) allows `enabled=false` to stop, while the [capacity guidance](https://docs.tokenfactory.nebius.com/ai-models-inference/dedicated-endpoints/capacity-and-scaling) warns that restarting releases and re-requests shared GPUs. No guaranteed model-loading/provisioning time, explicit minimum charge duration, account-specific custom-weights setup fee or storage/merge charge was established. The first charged minute would be **$0.0675 only under the base-H100-rate assumption**, not an exact minimum for this LoRA.

These are **illustrative arithmetic, not the exact estimated evaluation charge, a service-level commitment, or a provider-enforced cap**. They assume the same 1×H100 base rate can serve the fine-tuned BF16 weights *and* exact BF16 base, every stage fits the stated active minutes, and no further billable setup, storage, taxes, additional replicas or idle review time. None of those assumptions has been confirmed. Starting/stopping between stages may save active time but can lose GPU capacity; human review should occur offline with the endpoint stopped. A local BF16 base comparator could replace a paid second endpoint **if** compatible compute is available, but its actual cost has not been priced. Quantized `openai/gpt-oss-20b` is a proxy, **not** the identical BF16 base for a clean before/after inference comparison.

To produce an approval-ready **exact estimate**, obtain from Nebius the checkpoint's accepted artifact type (adapter vs merged), exact template/model ID and quantization, GPU type/count, per-minute price, minimum/rounding rule, charges for custom enablement/merge/storage, whether disabling immediately ends billing, and any realistic provisioning expectation. Confirm a route and cost for the identical BF16 base comparator. Then compute `billable minutes × verified price × replica/GPU count + documented extras` and set an explicit active-time cap. Stop if the quote materially differs from this scenario. **Do not create an endpoint until the user accepts the actual cost gate.**
